# EcoLink backend & AWS infrastructure

Serverless backend for the EcoLink WhatsApp assistant: DynamoDB, S3, API Gateway, Lambda
(Python 3.12), SNS, Cognito, Secrets Manager and Bedrock, defined with **AWS CDK (Python)**.
Messaging and voice sit behind interfaces (`MessagingProvider`, `VoiceProvider`); the shipped
adapter is **Twilio** (WhatsApp + programmable voice). Nothing in the deployed system is stubbed:
`/classify` calls a Bedrock vision model and `/agent/message` invokes the real agent Lambda.

```
 WhatsApp user ──► Twilio ──► POST /webhooks/messaging ──► Webhook Lambda ──► Agent Lambda (Strands + Bedrock)
        ▲                          (signature verified)      │  photo → private S3        │ tools call this API
        │                                                    │  (7-day expiry)            ▼
        └────────── reply via Twilio REST ◄──────────────────┘          /classify /price /ewaste/quote
                                                                         /recyclers/match /pickups ...
 Recycler phone ◄── Twilio voice call ◄── POST /voice/offer             (API-key authorizer, Secrets Manager)
        │  presses 1 / 2
        └──► POST /voice/response (signature verified) ──► pickup: offered → confirmed | declined
                                                            ├─► address + confirmation to recycler, confirmation to household
                                                            └─► SNS topic "pickup status"
 Ops dashboard ──► POST /auth/login ──► Cognito ID token ──► GET /pickups, /dashboard/* (admins / viewers)
```

## What is where

| Path | Contents |
|---|---|
| `backend/ecolink/handlers/` | One Lambda handler per concern: `pickups`, `recyclers_match`, `pricing`, `proxy` (`/classify`, `/agent/message`), `uploads`, `voice`, `messaging_webhook`, `authorizer`, `auth`, `dashboard` |
| `backend/ecolink/core/` | Logic: `matching` (haversine), `offers` (**address rule**), `pickup_service` (state machine), `pricing`, `classifier`, `storage`, `repository`, `dashboard_view` |
| `backend/ecolink/providers/` | `base.py` (interfaces), `twilio.py` (adapter, stdlib only), `__init__.py` (factory) |
| `backend/ecolink/schema.py` | The five DynamoDB tables: single source of truth for CDK, scripts and tests |
| `infra/` | CDK app (`app.py`, `ecolink_stack.py`) |
| `scripts/` | `put_secrets.py`, `seed.py`, `reset.py`, `smoke_test.py` |
| `tests/` | Backend tests (`test_matching.py`, `test_address_rule.py`, `test_backend_api.py`, `test_dashboard_api.py`, `test_env_and_secrets.py`) |
| `agent/` | The Strands agent, deployed by the same stack |

## What you need before deploying

| You need | Where to get it | Goes in |
|---|---|---|
| AWS account + credentials, region (default `ap-south-1`) | `aws configure`, or an AWS profile / keys | `.env`: `AWS_REGION`, optionally `AWS_PROFILE` / keys |
| Amazon Bedrock access to the model (default `apac.amazon.nova-pro-v1:0`) | Bedrock console → Model access, in the deploy region | `.env`: `BEDROCK_MODEL_ID` (optional) |
| Twilio **Account SID** and **Auth Token** | console.twilio.com dashboard | `.env`: `TWILIO_ACCOUNT_SID`, `TWILIO_AUTH_TOKEN` |
| Twilio **WhatsApp sender** (sandbox is `whatsapp:+14155238886`) | Twilio → Messaging → Try it out → WhatsApp | `.env`: `TWILIO_WHATSAPP_FROM` |
| Twilio **voice number** (voice-capable, E.164) | Twilio → Phone Numbers | `.env`: `TWILIO_VOICE_FROM` |
| A **real phone** to play the recycler (E.164) | Your phone. On a Twilio trial it must be a verified caller ID | `.env`: `RECYCLER_PHONE` |
| The **demo household's WhatsApp number** | Your phone. It must have joined the Twilio sandbox | `.env`: `DEMO_USER_ID` (`whatsapp:+91...`) |
| Tools | Python 3.11+, Node.js 18+, `npm i -g aws-cdk`, AWS CLI | |

`cp .env.example .env` and fill it in. `.env` is git-ignored; the Twilio values are copied into
**AWS Secrets Manager** by `scripts/put_secrets.py`, never into the repo, the template or the Lambda configuration.
The API key is generated by the stack in Secrets Manager (`ecolink/api-key`).

**If Secrets Manager is blocked on your account** (for example a new account on the AWS Free plan fails with
`AccessDeniedException ... explicit deny in a service control policy`), set `SECRETS_BACKEND=ssm` in `.env`. The same two
secrets are then stored as encrypted SSM Parameter Store `SecureString` parameters (`/ecolink/twilio`, `/ecolink/api-key`).
`put_secrets.py` writes them (it also generates the API key, because CloudFormation cannot create encrypted parameters) and
each Lambda gets `ssm:GetParameter` on exactly one parameter. Everything else is unchanged. This only helps if SSM itself is
not blocked; check with `aws ssm put-parameter --name /ecolink/probe --value x --type SecureString --region <region>`.

## Deploy

```bash
# 1. Python environment (Windows: .venv\Scripts\activate)
python -m venv .venv && source .venv/bin/activate
pip install -r infra/requirements.txt

# 2. Configure
cp .env.example .env            # then edit it

# 3. Store the Twilio credentials in Secrets Manager
python scripts/put_secrets.py

# 4. Deploy (first time in this account/region: cdk bootstrap)
cd infra
cdk bootstrap
cdk deploy                      # prints ApiUrl, TwilioMessagingWebhookUrl, UserPoolId, ...
cd ..

# 5. Load demo data (8 recyclers, sample household, rate table)
python scripts/seed.py
```

`cdk deploy` bundles the agent Lambda (about 63 MB) with `pip` using Linux/arm64 wheels, so Docker is not required; if pip
fails it falls back to bundling in Docker. Bundling needs a few hundred MB of free RAM (it failed with only ~350 MB free).

**6. Point Twilio at the stack** (Twilio console → Messaging → Try it out → Send a WhatsApp message → *Sandbox settings*):
set **When a message comes in** to the `TwilioMessagingWebhookUrl` output, method **POST**. Then, from the demo phone, send
`join <your-sandbox-code>` to the sandbox number. Voice needs no console configuration: the call's instructions and callback
URL are sent with each call. For calls to India enable *Voice → Settings → Geo permissions → India* in Twilio.

**7. Verify**

```bash
python scripts/smoke_test.py          # API, DynamoDB, S3 upload, Bedrock classify, agent reply
python scripts/smoke_test.py --call   # also rings RECYCLER_PHONE; press 1 (accept) or 2 (decline)
```

Then WhatsApp the sandbox number "hi". After the smoke test passes, the real flow is: photo → classification and
estimate → "yes" → the recycler's phone rings → press 1 → both of you get a WhatsApp confirmation and the
recycler's message contains the address.

**Create a dashboard user** (the `ApiUrl`/`UserPoolId` values come from the `cdk deploy` output):

```bash
aws cognito-idp admin-create-user --user-pool-id <UserPoolId> --username you@example.com \
  --user-attributes Name=email,Value=you@example.com Name=email_verified,Value=true --message-action SUPPRESS
aws cognito-idp admin-set-user-password --user-pool-id <UserPoolId> --username you@example.com \
  --password '<a 12+ character password>' --permanent
aws cognito-idp admin-add-user-to-group --user-pool-id <UserPoolId> --username you@example.com --group-name admins  # or viewers
```

Then set `mockMode: false` and `baseUrl` in `frontend/dashboard/config.js` and sign in.

**Restore the demo state** at any time: `python scripts/reset.py --yes` (add `--purge-images <ImagesBucketName>` to empty the bucket).
**Tear down**: `cd infra && cdk destroy` (deletes tables and bucket unless deployed with `-c retain_data=true`).

## API

All JSON. Errors are always `{"error": "<code>", "detail": "<human readable message>"}` with a meaningful status
(400 invalid input, 401/403 auth, 404 unknown id, 409 invalid state change, 422 hazardous item, 502 upstream failure).
"API key" = `Authorization: Bearer <key from Secrets Manager ecolink/api-key>`.

| Route | Auth | Notes |
|---|---|---|
| `POST /classify {image_url}` → `{items:[{label,confidence,hazardous}]}` | API key | Bedrock vision. `image_url` must be https on a public host (pre-signed S3 URLs work); private/loopback/metadata addresses are refused. |
| `GET /price?label=&weight_kg=` → `{low,high,currency:"INR",updated}` | API key | From `rate_table`; `ewaste`/`battery` return 422 (use the quote endpoint). |
| `POST /ewaste/quote {item_type,age_years,condition}` → `{low,high,recommendation}` | API key | `sell` if the estimated high ≥ Rs 500, else `dropoff`; batteries are always `dropoff`. |
| `GET /recyclers/match?lat=&lng=&labels=` → `[{recycler_id,name,distance_km,accepts}]` | API key | Available recyclers that accept **all** labels (`mode=any` for at least one), nearest first. Also `limit`, `max_km`. |
| `POST /pickups {user_id,items,address_text,slot}` → `201 {pickup_id,status}` | API key | Hazardous labels are rejected here too (422). `slot` is ISO 8601. |
| `PATCH /pickups/{id} {status}` | API key | Enforces the state machine below. `offered` can only be set by `/voice/offer`. |
| `POST /agent/message {user_id,text,image_url?,lang}` → `{reply_text,actions}` | API key | Invokes the agent Lambda. |
| `POST /voice/offer {pickup_id,recycler_id}` | API key | Phones the recycler (pickup `requested`/`declined` → `offered`). The offer never contains the address. |
| `POST /voice/response {pickup_id,digit}` | Twilio signature **or** API key | `1` → `confirmed`, `2` → `declined`. Twilio posts `Digits` as a signed form with `pickup_id` in the query string; other callers may send the JSON contract body with the API key. |
| `POST /webhooks/messaging` | Twilio signature | Inbound WhatsApp. Stores photos privately, calls the agent, replies via Twilio. |
| `POST /uploads/presign {user_id,content_type}` | API key | Pre-signed S3 POST limited to one key, one image type, ≤ 5 MB; returns a pre-signed GET `image_url` for `/classify`. |
| `POST /auth/login {email,password[,new_password]}` | none | Cognito sign-in for the dashboard → `{id_token,expires_in,user,group}`. |
| `GET /pickups`, `GET /pickups/{id}` | Cognito ID token | Dashboard views; `Authorization: <idToken>` (no `Bearer`). |
| `GET /dashboard/recyclers`, `GET /dashboard/users`, `PATCH /dashboard/pickups/{id}` | Cognito ID token | Users are joined with conversation state; the latter is `admins` only. |

**State machine:** `requested → offered | cancelled`; `offered → confirmed | declined | cancelled | requested`;
`declined → offered | requested | cancelled`; `confirmed → completed | cancelled`. Same-status requests are idempotent.
`confirmed` also requires an assigned recycler.

## The address rule

*A household's address is shared with a recycler only after the recycler accepts.* Enforced in one place,
`core/offers.py`, by whitelist builders instead of copying the pickup record:

- `recycler_view()` builds every recycler-facing payload (voice offer, confirmation message). `address_text` is
  included only when status is `confirmed` or `completed`; household id, notes and image links are never included.
- Before a call is placed `assert_no_address()` re-checks the payload and the service refuses to call if it leaks.
- Dashboard views (`core/dashboard_view.py`) apply the same rule to non-admins, and hide the household's coordinates
  with the address. SNS events carry ids, statuses and timestamps (the household id, never the address).
- `confirmed` is reached by the recycler's keypad press (signed callback); a trusted API client can also PATCH
  `offered → confirmed`, which the state machine only allows after a real offer.

## ML model fallbacks (weights in S3)

The stack creates a private, versioned **models bucket** (`ModelsBucketName` output) and uploads these files into it on
every `cdk deploy`:

| S3 key | Local file | Used by |
|---|---|---|
| `vision/best.onnx` | `ml/vision/artifacts/weights/best.onnx` | `/classify` fallback (YOLOv8n detector, run with ONNX Runtime) |
| `vision/best.pt` | `ml/vision/artifacts/weights/best.pt` | stored as the source checkpoint; not loaded at runtime |
| `pricing/rate_table.json` | `ml/pricing/rate_table.json` | `/price` and `/ewaste/quote` fallback rates |

- **`/classify`** tries Bedrock first and, if it fails with a server-side error (not verified, denied, throttled, down),
  answers with the local model instead. `CLASSIFY_PRIMARY=onnx` in `.env` reverses the order. The response keeps the contract
  (`{items:[{label,confidence,hazardous}]}`) and adds `source`: `bedrock` or `onnx-yolov8n`. The local model follows
  `ml/vision/config/inference.yaml`: 416 px input, confidence >= 0.50, NMS IoU 0.45, one entry per label, `ewaste` and `battery`
  always hazardous.
- **`/price` and `/ewaste/quote`** read DynamoDB first; if a rate is missing (table not seeded) or DynamoDB fails, they use
  `pricing/rate_table.json` from the models bucket. The arithmetic is the same; every number remains an estimate. There is no
  trained price model: pricing is the rule table described in `ml/pricing/ASSUMPTIONS.md` (its values are placeholders).
- **Why ONNX and not `best.pt`:** running `best.pt` needs PyTorch + ultralytics (hundreds of MB), which does not fit a Lambda zip.
  `best.onnx` is the export of the same checkpoint (the export report records a maximum confidence difference of 2e-06 over 50
  images), and runs with onnxruntime + numpy + Pillow in a ~120 MB layer built by the stack (`infra/ml-layer/`).
- **Updating the model:** replace the files under `ml/`, run `cdk deploy`. A hash of the files is passed to the Lambdas
  (`MODEL_VERSION`) so containers never keep a stale copy; older versions stay in the versioned bucket.
- The local model runs inside `ProxyFn` (1536 MB). The first classification after a cold start downloads the 12 MB model.
- Fidelity: the fallback resizes with an OpenCV-equivalent bilinear written in numpy (Pillow's resize low-pass filters and shifts the model's confidences). On ultralytics' sample photos at a 0.05 threshold it returned the same labels as ultralytics running the same `best.onnx` on 9 of 10 inputs, with a mean confidence difference of 0.003. Against ultralytics running `best.pt` it is looser (6 of 10 labels), but that gap is the ONNX export itself: ultralytics' own ONNX and PT outputs also agree on only 6 of 10 (the `.pt` model runs with rectangular padding, the fixed-size ONNX model with square). `scripts/check_vision_fallback.py` repeats the comparison on your own photos.

## Security & IAM

- Every Lambda has its own role with only the actions it uses, scoped to specific table/index/bucket/secret/function
  ARNs (see `infra/ecolink_stack.py`); Bedrock is limited to the configured model and its inference profile.
- Secrets live in Secrets Manager (`ecolink/api-key`, `ecolink/twilio`); the agent reads its key from there at runtime.
- S3: block-all-public-access, SSL-only, encrypted, objects expire after 7 days; keys contain a hash of the user id, not
  the phone number; inbound photos are copied to S3 and then **deleted from Twilio**.
- Webhooks verify Twilio's HMAC signature; the API key is compared in constant time; API Gateway throttles to 50 req/s.
- The stack does not modify the account-wide API Gateway logging role.

## Tests

```bash
pip install -r requirements-dev.txt
python -m pytest tests
```

The backend tests run the **real handlers and boto3 code** against `moto` (an AWS emulator: DynamoDB with the real table
schema, S3, SNS→SQS, Secrets Manager, Cognito) and make real HTTP calls to a local server standing in for Twilio's
REST API; inbound webhooks are signed with Twilio's real algorithm. They include the unit tests for match logic and the
address rule (which fail if the rule is weakened). Not covered by tests, because they need real accounts: the Bedrock
call itself, Twilio media download from `*.twilio.com`, and live phone calls. `scripts/smoke_test.py` exercises those on a
deployed stack.

## Limitations & decisions

- **Webhook is synchronous.** Twilio expects a webhook response within ~15 s; a slow agent turn can log a Twilio timeout
  warning, but the reply is still delivered because it is sent through Twilio's REST API. Repeated deliveries of the same
  inbound message are not de-duplicated.
- **Unanswered calls:** the call rings for 30 s; the pickup then stays `offered`. An admin (or API client) can set it back to
  `requested` and offer it to another recycler.
- **One demo phone:** the seed gives all eight recyclers the same `RECYCLER_PHONE`, so any match rings your phone.
- **Matching scans the recyclers table**, which is fine for tens of recyclers; add a geohash index before scaling.
- **Pre-signed URLs** handed to the agent are valid for 1 hour (`IMAGE_URL_TTL_SECONDS`); the stored object itself lives 7 days.
- **Agent dependency pin:** `agent/requirements-lambda.txt` pins `strands-agents==0.1.9` as the repo did;
  `strands-agents-builder` from the root `requirements.txt` is a CLI and is not bundled.
- **Bedrock model/region:** `apac.amazon.nova-pro-v1:0` is the cross-region profile usable from `ap-south-1`; use `us.*` /
  `eu.*` profiles in those regions via `BEDROCK_MODEL_ID`.
- **Frontends are not hosted by this stack** (`site/`, `dashboard/` are static files).

## Troubleshooting

| Symptom | Likely cause |
|---|---|
| WhatsApp gets no reply | Sandbox webhook URL not set to `TwilioMessagingWebhookUrl`; phone has not joined the sandbox; check the *Webhook* Lambda log group |
| `403 invalid_signature` in Lambda logs | Twilio signs the exact URL: use the stack output unchanged (`https://.../prod/webhooks/messaging`); behind a custom domain set `-c public_base_url=...` |
| Voice call never rings | Trial account: `RECYCLER_PHONE` not a verified caller ID; India geo-permission disabled; check the *Voice* Lambda log |
| `502 classifier_error` | Bedrock model not enabled in the region, or `BEDROCK_MODEL_ID` is a profile for another geography |
| `503 not_configured` from `/agent/message` | `AGENT_FUNCTION_NAME` missing (deploy through the stack) |
| Dashboard 401 | Send the Cognito **ID token** as the raw `Authorization` header; token lasts 1 hour |
| `cdk deploy` fails with `MemoryError` in pip | Low free RAM during agent bundling; close applications and retry |
